# GameLife V0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 做出一台 macOS 常驻托盘应用：15 秒采样估计有效主线时间，灰区才看图，按秒累计 480 分钟 Gold Day，硬币/能量只赚不扣。

**Architecture:** 可单测的纯 Rust 库 `gamelife-core` 承载判定、观测缺口、账本、连胜、商店规则；`src-tauri` 只做 SQLite、macOS API、托盘调度和把 core 的结果落盘；`src/` 是 React 主窗口。所有经济写入走幂等键 + 事务。

**Tech Stack:** Tauri 2、React、TypeScript、Rust、rusqlite、chrono、macOS Keychain、OpenAI 兼容视觉 API。

**Spec:** `docs/superpowers/specs/2026-09-10-gamelife-design.md`

## Global Constraints

- 采样间隔固定 15 秒，设置页不得出现间隔旋钮。
- `0 ≤ credited_core_seconds ≤ observed_seconds ≤ actual_slot_duration ≤ 900`。
- 相邻样本间隔 `> 30s` 的中间段必须是 unobserved，禁止按两端 Core 外推。
- 硬币只 earn/spend，ledger 禁止惩罚性负硬币；XP 禁止清零负分。
- Gold Day（当天 credited ≥ 28800）之后不再产生 Coin 或 XP。
- `capture_scheduled_at` 开槽写入后禁止改抽签；错过标 missed，禁止立即补截。
- API Key 只进钥匙串；截图默认 `frontmost_window`，用完即删。
- Never Capture 内置项每一条不可删除；GameLife 自身为不可删除 Side Project 规则。
- UI 文案「估计有效主线」，显示到分钟（`5h 23m`），不显示秒。
- 已 `final` 槽不得改经济结果；只能 Report misclassification。
- 无 `support_counts_as_core` 开关。
- V0.1 不做健康数据、摄像头、手机端、云同步、追溯冲正。

### Task 4: 观测跨度（不外推）与心跳 unobserved

**Files:**
- Create: `crates/gamelife-core/src/observe.rs`
- Create: `crates/gamelife-core/src/heartbeat.rs`

**Interfaces:**
- Consumes: `SAMPLE_INTERVAL_SECS`, `MAX_GAP_SECS`, `Hint`, `Sample`
- Produces:
  - `pub enum SpanKind { Observed(Hint), Unobserved }`
  - `pub struct Span { pub start: i64, pub end: i64, pub kind: SpanKind }`
  - `pub fn spans_for_slot(samples: &[Sample], hints: &[Hint], slot_start: i64, slot_end: i64) -> Vec<Span>`
  - `pub fn observed_seconds(spans: &[Span]) -> i64`
  - `pub fn heartbeat_unobserved(last_heartbeat: i64, now: i64, last_heartbeat_local_date: chrono::NaiveDate, now_local_date: chrono::NaiveDate) -> Vec<(i64, i64)>`

`spans_for_slot` 规则（spec 7.1）：

- 样本按 ts 排序。`hints.len() == samples.len()`。
- 槽起点到第一条样本：若 `first.ts - slot_start > MAX_GAP_SECS`，则 `[slot_start, first.ts)` 里只有 `[first.ts - SAMPLE_INTERVAL, first.ts)` 与样本相接的部分视为 observed 太晚——**简化为**：`[slot_start, first.ts)` 全部 Unobserved（中途启动 / 半截槽开头）。
- 相邻 `t0, t1`：若 `t1-t0 <= 30`，`[t0,t1)` Observed(hint0)；若 `t1-t0 > 30`，`[t0, t0+15)` Observed(hint0)（夹在 `t1` 内），`(t0+15, t1)` Unobserved。
- 最后样本到 `slot_end`：同样 30s 规则。
- 所有 span `end > start`，总和等于 `slot_end - slot_start`。

心跳：

- 同一 `NaiveDate`：返回 `vec![(last_heartbeat, now)]`（若 `now > last`）。
- `now_local_date > last_heartbeat_local_date`：只返回缺口到「调用方传入的心跳日结束 epoch」——因此签名改为：

```rust
pub fn heartbeat_unobserved(
    last_heartbeat: i64,
    now: i64,
    same_local_day: bool,
    end_of_heartbeat_local_day: i64,
) -> Vec<(i64, i64)>
```

- `same_local_day == true`：`(last, now)`
- `false`：若 `end_of_heartbeat_local_day > last`，`(last, end_of_heartbeat_local_day)`，**不含** 今天 00:00→now

```rust
    pub activity: ActivitySeconds,

    pub pending: bool,
}

pub fn judge_slot(input: JudgeInput<'_>) -> JudgeOutput
```

实现顺序（必须写进代码注释并测试）：

1. 对每条 sample 调 `hint_sample`（维护 `last_core_interaction_ts`：idle<180 且 hint 会是 CoreCandidate 时更新）。
2. `spans_for_slot` → 累加 `activity`：Unobserved→unobserved；Observed(Side)→side；Distraction→distraction；Away→away；CoreCandidate（且该样本 idle<180）与 CoreReading→先记入内部 strong/bridge；Unsure/UnsureReading 暂不进 core。
3. `observed_seconds` = 非 Unobserved 秒数。`actual = slot_end - slot_start`。
4. `strong_core` / `reading_bridge`（bridge cap 300）从 span 秒数统计。
5. `verified_core = 0`。
6. 分支：
   - `unobserved == actual` → Dominant::Unobserved，credited=0
   - away≥600 且 strong_core<300 → BreakAway，credited=0，不用视觉
   - strong_core≥780 且 side+distraction≤60 → CoreResearch，credited=`strong+bridge`，不用视觉
   - side+distraction≥300 且 > strong+bridge → Side 或 Distraction（谁大），credited=0
   - 否则灰区：若 `manual_core == Some(true)` 或 (`vision.wants_core && confidence>=0.7`)：把 span 中 Observed(Unsure|UnsureReading) **且**（若 `context_app` 有值则 `sample.app` 与之大小写相等；若无人审且无 context_app 则不升级）**且** 不是 side/distraction/away 的秒数加入 `verified_core` 和 `activity.core`。人审 Core 时不要求 context_app。
   - 视觉 wants_core 但 metadata strong_core>0 且 context 对不上 → pending
   - 无视觉且 capture Missed/Skipped 且灰区 → pending
   - pending 时 credited=0
7. 最终 `credited = min(observed, actual, strong_core + reading_bridge + verified_core)`，且 `<=900`。
8. `quests` 为空时 credited 强制 0，且不得自动 CoreResearch（可 pending/unobserved）。

```rust
pub struct RewardEvent {
    pub key: String,
    pub coin: i64,
    pub xp: i64,
}

pub fn tick_keys_for_credited(day: &str, before: i64, after: i64) -> Vec<RewardEvent>
```

`day` 为 `YYYY-MM-DD`。

规则：

- `let cap = GOLD_DAY_SECS;` 若 `before >= cap`，返回空（Gold Day 后无 coin/xp）。
- `let after_c = after.min(cap);`
- Coin ticks：`n = (after_c / 900).min(32) - (before.min(cap) / 900).min(32)`，keys `validated_coin:{day}:{i}` i 从 old+1 到 new，coin=1, xp=0。
- XP ticks：`n = (after_c / 90).min(320) - (before.min(cap) / 90).min(320)`，keys `validated_xp:{day}:{i}`，xp=1, coin=0。
- 阶梯：当 `before < T <= after`（T in 7200,14400,21600,28800）发 `ladder:{2h|4h|6h|8h}:{day}`，coin 分别为 1,2,3,5。若 `before >= GOLD_DAY_SECS` 不发（已由空返回覆盖）。

另：`pub fn support_xp_key(day: &str, slot_start: i64) -> RewardEvent` 仅当调用方确认尚未 Gold Day：key `xp_support:{day}:{slot_start}` xp=6。`pub fn admin_xp_key(...)` xp=2。这些函数本身不查 Gold Day，由调用方保证；测试里单独测 tick 封顶。
